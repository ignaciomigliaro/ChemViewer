# Project: Reverse Engineer Chemcraft and Build a Fully Functional macOS Version

You are an expert reverse-engineering engineer, macOS software developer, and computational chemistry software architect.

Your task is to investigate Chemcraft, understand how the Windows application works, and develop a fully functional, reliable macOS application with feature parity.

**This is an implementation project, not just a research or documentation task.** I want a working application that I can use daily for computational chemistry.

## 1. Primary objective

Chemcraft is a molecular visualization and computational chemistry analysis program.

Official website:
https://www.chemcraftprog.com/

Windows download:
https://www.chemcraftprog.com/download.html

macOS beta:
https://chemcraftprog.com/MacVersion.html

Documentation:
https://www.chemcraftprog.com/help.html

The Windows version works significantly better than the existing macOS beta.

I want to use Chemcraft on an Apple Silicon Mac with all the functionality of the Windows version.

The ultimate deliverable should be a reliable macOS `.app` application, ideally running natively on Apple Silicon without requiring Wine, CrossOver, or a Windows virtual machine.

The application must preserve the scientific functionality, numerical accuracy, interaction behavior, file compatibility, and usability of Chemcraft.

Do not consider the project complete simply because a window opens.

Use REA (Reverse Engineer Anything) as the primary reverse-engineering tool where appropriate:

https://github.com/morluto/rea

You may also use:

First discover which tools are installed and which MCP servers are available. Do not assume that a tool, computer, or application is accessible unless you verify it.

If the Windows and Mac environments are separate, design a reproducible workflow for gathering analysis evidence on Windows and transferring only the necessary development artifacts to macOS.

## 3. First investigate the existing macOS version

Before attempting to reimplement the application, investigate why the current macOS version is unreliable.

Determine:

1. Whether the official Mac ARM build can launch on the target machine.
2. Whether its crashes are caused by missing dependencies, incorrect file permissions, application signing, quarantine, graphics rendering, unsupported APIs, threading, or architecture incompatibilities.
3. Whether some features are broken while others work.
4. Whether the Intel version behaves differently under a compatible execution environment.
5. Whether a lawful, noninvasive compatibility fix can make the existing program reliable.

Capture crash reports and reproduce failures systematically.

Do not automatically remove security protections or modify system security settings.

If the existing macOS application can be repaired sufficiently to deliver full functionality, prioritize that approach. If the defects cannot be resolved without proprietary source code, document the evidence and proceed to the next strategy.

## 6. Determine the best implementation approach

Compare these strategies:

**Strategy A — Repair the official macOS version.**

Fix identifiable compatibility and runtime problems where technically possible without modifying protected proprietary functionality or circumventing licensing.

**Strategy B — Run the Windows implementation through a compatibility layer.**

Investigate whether a properly configured Wine or CrossOver environment can provide full feature parity and reliable performance on Apple Silicon. Treat this as a fallback or temporary solution.

**Strategy C — Develop a native macOS implementation.**

Create an independently implemented application using documented formats, observed behavior, and original source code.

Prefer native Apple Silicon execution for the long-term solution.

Evaluate feasibility, maintenance burden, scientific correctness, compatibility, and achievable feature parity before committing to a strategy.

Do not spend excessive effort attempting to reconstruct the original proprietary source code when an independent implementation or existing native fix is more practical.

## 7. Native macOS architecture

If developing an independent implementation, use a modular architecture separating:

1. Scientific file parsers.
2. Molecular data models.
3. Geometry editing.
4. Rendering and volumetric visualization.
5. Computational chemistry analysis.
6. Plotting and animation.
7. macOS graphical user interface.
8. Import/export functionality.

Use an appropriate native rendering technology, preferably Metal where suitable.

Design the codebase so additional computational chemistry formats can be added without rewriting the UI.

Use verified, maintained libraries when possible instead of reinventing established algorithms.

The application should remain responsive while parsing large output files or calculating molecular surfaces.

## 8. Scientific validation

Construct a test suite using representative quantum chemistry results.

- Geometry optimizations.
- Transition-state optimizations.
- Frequency calculations.
- NEB pathways and reaction profiles.
- IRC calculations.
- Molecular orbital analysis.
- Potential energy surface scans.

Use regression tests to ensure scientific calculations remain consistent after changes.
